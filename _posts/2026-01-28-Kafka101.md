Consider a fictional e-commerce platform. Every time an order is placed on this platform several operations need to work. The order needs to be assigned a shipping partner (performed by the Shipping service), the order needs to update the count of this product in inventory (performed by the Inventory service) being examples of such work. One option would be to call each service synchronously. In this case, the Order service makes a simple HTTP call to the Shipping service and the Inventory service in it’s order creation code.

```
public void createOrder(Order order) {

    // Blocking call to Inventory Service
    boolean inventoryReserved =
            inventoryService.reserve(
                    order.getProductId(),
                    order.getQuantity()
            );

    if (!inventoryReserved) {
        throw new RuntimeException("Out of stock");
    }

    // Blocking call to Shipping Service
    shippingService.createShipment(order);

    // Continue order creation
    saveOrder(order);
}
```

Problems arise with this approach when either the inventory or shipping service is down or already overloaded. In such cases, the downstream services (shipping and inventory) either miss an order that was created or the upstream service keeps waiting for these services to respond (slowing down the order service too). This problem of coupling is what led to Kafka being widely used. 

Fundamentally Kafka is an event streaming platform. Producer/s publish events to a Kafka cluster and Consumer/s can consumer and process those events. The producer can produce at its own speed and the consumer can consume at its own speed. There are several advantages of decoupling your services. In our original example, we will need to change the order creation code if there is a new task that needs to run when an order is created. In Kafka, we can add as many consumers as we want and it would not affect the producer.

An event is an immutable record of something that has happened. Unlike messaging services like RabbitMQ, Kafka does not delete messages on consumption. Events are grouped into topics. Topic is simply a collection of similar events. In our case `orderCreated` would be a topic. Whenever a new order is created, an event is published to this topic. As the number of orders grow, a single Kafka node would not be able to handle all the messages being published. To solve this problem of horizontal scaling, we can divide a topic into partitions. Messages are then distributed among the partitions (partitioning logic could be round robin or based on a key).

As you scale, you might need more consumers for a service. Consumer groups allow you to group several consumers to subscribe to a topic, distributing the load between them. One partition can be consumed by only one consumer in a group. This allows for horizontal scaling of consumers as well. Consumers read from a partition by providing the last offset they read till. Offset is an index that is used to order messages in a partition. As offset only increase, the order within a partition is maintained.
